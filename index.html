WINK STORE WINKSTORE

An Arabic-first, right-to-left beauty store for Palestine with verified cash-on-delivery checkout. One commerce backend runs the web storefront, an iOS and Android app built with Expo, and the admin dashboard.

Problem

  1. One commerce backend for web, mobile and admin

    The Next.js storefront, the Expo app and an Arabic admin dashboard share one Medusa v2 API, one design-token package and shared validation, so business rules stay the same on every platform.

  2. Cash-on-delivery checkout with order verification

Testing evidence

Challenges and solutions

  • Cancelled orders kept stock off sale.

    Each lifecycle step now runs the matching commerce workflow (fulfil, capture, complete, return and restock), and a dry-run-first repair script brings older orders back in line.

  • Messages dropped when handlers competed.

    Handlers now claim the work, send without holding the order, then record the result; a stale claim expires on its own.

  • A retry could repeat a delivered message.

    Before any retry, the system checks whether the message already went out, and sends nothing when the answer is uncertain.

  • Strict security policy versus caching.

    Catalogue pages use a cacheable policy; checkout and account pages keep a strict per-request one.

03 — Engineering lab · Open source

Agent TrustAGENTTRUST

An authorization layer for AI agents. Instead of a trust score, every action has to be backed by verifiable, scoped and revocable authority, and a deterministic policy makes the decision.

  • Verifiable identity

    Agents identify with W3C decentralized identifiers and prove possession of their key on every request.

  • Scoped delegation

    Authority arrives as W3C Verifiable Credentials, and delegated authority can only narrow, never widen.

  • Deterministic policy

    Rego policies compiled to WebAssembly run inside the service and return ALLOW, DENY or REQUIRE_APPROVAL with a reason code, failing closed.

TypeScript · Fastify · Next.js · Redis · OPA (Wasm) MIT licence · runs locally with Docker Compose · no hosted demo View the repository on GitHub

Inside the engineeringInside theengineering

Five decisions from the projects above: the problem, what I chose, and the evidence behind it. Everything here comes from the case studies on this page.

WINK STORE · Event processing

WhatsApp messages that are never sent twice

Problem

Order confirmations go out from background event handlers. Competing handlers dropped messages, and a retry after a crash could repeat one that had already been delivered.

Decision

A handler claims the work, sends without holding the order, then records the result; a stale claim expires on its own. Before any retry it checks whether the message already went out, and sends nothing when the answer is uncertain.

  1. Claim
  2. Send
  3. Record
  4. Retry: check first

ContextListed under WINK STORE's challenges and solutions. The backend has 583 automated tests (project audit, 27 Sep 2026), and the project keeps a recorded reliability and security review of 19 findings, each with its fix.

WINK STORE · Commerce workflows

Every order step runs the matching commerce workflow

Problem

Cancelled orders kept their stock off sale, because the store's order states and the commerce engine's stock, payment and fulfilment records drifted apart.

Decision

Each lifecycle step staff take now runs the matching workflow in the commerce engine: fulfil, capture, complete, or return and restock. A dry-run-first repair script brings older orders back in line.

  1. Confirm
  2. Fulfil
  3. Capture
  4. Complete
  5. Cancel: return + restock

ContextCash-on-delivery orders are verified with a one-time WhatsApp code before they enter this lifecycle. The store is pre-launch and runs on an illustrative demo catalogue.

TOTAL PRINT · Background workers

A nesting engine that runs off the interface thread

Problem

Nesting thousands of pieces on a roll is heavy computation. Run on the interface thread, it would freeze the app while the shop waits for a layout.

Decision

The engine runs in a Web Worker: several first-fit-decreasing orderings, maximal-rectangles packing and local refinement. It was then profiled and the slow path fixed.

  1. Read sizes from files
  2. Order pieces
  3. Pack rectangles
  4. Refine
  5. Preview

EvidenceIn the project's engine audit (Aug 2026), layout time for a 5,066-item job fell from 3.97 s to 1.55 s (2.57×), with the same roll length and utilisation. One workload, measured by calling the engine directly on Windows 11 and Node 24, not through the interface.

TOTAL PRINT · Testing

Shared placement logic for preview and PDF export

Problem

If the layout on screen and the exported PDF disagree, the wrong thing is printed on expensive roll media.

Decision

The on-screen preview and the PDF exporter share one placement module instead of two copies of the same maths, and a test cross-checks them.

  1. Engine result
  2. One placement module
  3. Preview
  4. PDF

EvidenceA cross-check test over 432 configurations verifies that placement stays consistent between preview and PDF within those tested cases. PDF export is still being hardened before release; it is not claimed to be correct for every layout.

AGENT TRUST · Authorization

Authority you can verify, decided by a policy that fails closed

Problem

A trust score says nothing about what an AI agent is actually allowed to do, or who allowed it.

Decision

Agents prove their identity with decentralized identifiers, carry scoped authority as Verifiable Credentials that can only narrow when delegated, and a Rego policy compiled to WebAssembly returns ALLOW, DENY or REQUIRE_APPROVAL with a reason.

  1. Identity
  2. Credential
  3. Authority
  4. Policy
  5. Deny by default

EvidenceIn the repository's local demo, the same agent with the same valid credential is denied a 5,000 SAR refund because it exceeds its delegated 500 SAR limit. Open source under the MIT licence; no hosted demo.
